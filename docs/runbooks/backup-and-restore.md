# Runbook: database and object backup and restore

**When:** scheduled (every 15 minutes, automatic; integrity check daily), and on any loss or corruption of the application database, the Temporal persistence database, or the assets or releases bucket.
**Owner:** platform on-call. **Targets (RA-13, PR-09):** recovery point objective 15 minutes, recovery time objective 4 hours, for the databases and the objects. **Exercised:** locally by `tooling/scripts/db-backup/db-backup.test.ts` (object backup, object restore, verify, guards, against an AWS CLI stand-in) and `tooling/scripts/db-backup/db-backup.integration.test.ts` (backup, verify, restore and drill against MySQL); the database restore drill on Railway staging with `restore.sh` (timed `RESTORE_STEP` lines; the result is recorded in `docs/release/completion-ledger.md`). **Needs a live environment for:** the timed full drill (`drill.sh`, section "Recovery drill") with objects and the application steps.

## What runs

The `db-backup` service in each Railway environment is built from `infra/railway/db-backup/Dockerfile` (`mysql:9` client tools plus the AWS CLI) and runs `backup.sh` on the service's cron schedule (`*/15 * * * *`, restart policy never, Dockerfile path and watch pattern `infra/railway/db-backup/**` set in the service settings; Railway no longer reads `railway.json`). The service must run in the same region as the MySQL service (`us-west2`): a new service defaults to another region and the dump then crawls at one round trip of about 140 ms per statement. Each run has two halves, run as separate processes so that a failure of one never skips the other; the run exits 1 when either failed:

1. **Databases.** Dumps `SRC_DB` from `SRC_HOST` (the application database) and, when `SRC2_HOST` is set, `SRC2_DB` from `SRC2_HOST` (the Temporal persistence database) with `mysqldump --single-transaction --routines --triggers --events`. When binary logging is on, `--source-data=2` records the binlog position in the dump.
   - Gzips each dump and checks that it is complete before anything is uploaded: mysqldump's own exit status is captured from inside the pipeline (the image's `/bin/sh` may be dash, which has no `pipefail`, so the pipeline's status alone is gzip's), and the dump must end with mysqldump's `-- Dump completed` trailer. A dump that died part-way (a lost connection, a killed process) or lacks the trailer prints `DB_BACKUP_FAIL <name> …: dump incomplete, nothing uploaded` and exits 1, and neither the dump nor a sidecar is written to the store.
   - Copies each complete dump to `s3://$BACKUP_BUCKET/$BACKUP_PREFIX/<name>/<name>-<UTC stamp>.sql.gz` (`oremedia` and `temporal`), confirms the stored size with a head request, then uploads the **sha256 sidecar** `<dump>.sha256` (`sha256sum` format: the hash and the dump's file name). The sidecar goes up only after the dump is confirmed, so a sidecar always names a complete dump.
   - Keeps a local copy on the service volume when `BACKUP_LOCAL_DIR` (default `/backups`) exists, and deletes dumps and sidecars older than `BACKUP_RETENTION_DAYS` (default 14) from the store and the volume.
   - Prints one `DB_BACKUP_PASS <name> s3://… <size> bytes binlog=<0|1> sha256=<hash>` line per database and `DB_BACKUP_DONE`, or `DB_BACKUP_FAIL …` and exits 1. A dump under 1 KiB is a failure, not a success.
2. **Objects** (`object-backup.sh`). Copies new or changed objects of the assets and releases buckets (`OBJECT_STORE_BUCKET_ASSETS`, `OBJECT_STORE_BUCKET_RELEASES`, once each when they are the same bucket) from the application's object store into the backups bucket, under `$OBJECT_BACKUP_PREFIX/<bucket>/` (default `object-backups/<environment>`):
   - `objects/<sha256>`: each distinct content once, immutable (content-addressed; two keys with the same bytes share it).
   - `manifests/manifest-<UTC stamp>.tsv.gz`: one per run, the whole catalog after the run, one row per key: `state` (`live`, or `gone` for a key deleted from the source or replaced by new content), `sha256`, `size`, `ETag`, content type, `since` (the run that copied it, or that saw it go) and the key. Restores read it and verify every object against its `sha256`.
   - `cursor`: the last key handled when a run stopped at its bound.
   - An object is copied when its key has no live catalog row with the same size and ETag; it is downloaded, hashed, checked against the size the store reported, and its content uploaded unless that `sha256` is already in the backup. Reruns are safe: an unchanged object is not downloaded again and known content is not uploaded again; a run interrupted half way leaves content without a manifest row, which the next run finds and records.
   - **Copy only.** Nothing is written to or deleted from a source bucket (the application store is only listed and read; use read-only credentials). A key that leaves the source stays in the catalog as `gone` with its content for `BACKUP_RETENTION_DAYS`, as dumps do, then the row is dropped and its content deleted unless another row still references it. Manifests older than the window are deleted (the newest is always kept), so every manifest still present is fully restorable.
   - **Bounded.** A run copies at most `OBJECT_BACKUP_MAX_OBJECTS` objects (default 300) and `OBJECT_BACKUP_MAX_BYTES` (default 1 GiB, always at least one object). The rest carries over: the next run starts after `cursor` and wraps around, so a key that keeps failing never starves the keys after it. `OBJECT_BACKUP_CARRYOVER <bucket> <n> objects left for the next run` reports it.
   - `quarantine/` (unscanned uploads) is excluded by default (`OBJECT_BACKUP_EXCLUDE_PREFIXES`, space separated). A key outside the application's key pattern (letters, digits, `_ . - /`) is reported (`OBJECT_BACKUP_UNSUPPORTED_KEY`) and fails the run rather than being parsed.
   - Prints `OBJECT_BACKUP_MANIFEST <bucket> s3://… live=<n> gone=<n>`, then `OBJECT_BACKUP_PASS <bucket> <copied> <bytes>` per bucket, or `OBJECT_BACKUP_FAIL <bucket> <reason>` and exits 1. A download error fails the run but keeps every other copy of that run (the manifest is still written). When neither bucket variable is set the half prints `OBJECT_BACKUP_SKIPPED` and the verify job fails.

Railway's managed MySQL has no point-in-time recovery, so the dump is the recovery point. A 15-minute cadence gives an RPO of at most 15 minutes plus the dump time; for objects, 15 minutes plus the copy time, as long as uploads between two runs stay under the per-run bound (a `CARRYOVER` line means the bound was hit: raise it, or expect the backlog to clear over the next runs). The first run of an environment copies the existing objects over several runs (300 per run by default). Each manifest is the whole catalog, gzipped (roughly 100 bytes per object), and one is written every run, so a 14-day window holds about 1,350 manifests per bucket: about 1.3 GB for 10,000 objects. Content uploaded by a run that failed before writing its manifest is recorded by the next run; content of a key that vanished before any manifest recorded it stays until removed by hand (no orphan sweep).

## Integrity check (`verify.sh`, daily)

A second cron service, `db-backup-verify`, runs the same image with start command `verify.sh` once a day (`47 5 * * *`, restart policy never, same region). It is read-only and needs only the backups store and the bucket names: `OBJECT_STORE_ENDPOINT`, `OBJECT_STORE_ACCESS_KEY_ID`, `OBJECT_STORE_SECRET_ACCESS_KEY`, `OBJECT_STORE_REGION`, `BACKUP_BUCKET`, `BACKUP_PREFIX`, `OBJECT_BACKUP_PREFIX`, `OBJECT_STORE_BUCKET_ASSETS`, `OBJECT_STORE_BUCKET_RELEASES` (references to the `db-backup` service's variables) and `VERIFY_NAMES` = `oremedia temporal`. It checks:

1. For each name in `VERIFY_NAMES` (default `oremedia`, plus `temporal` when `SRC2_HOST` is set): the newest dump is at most `VERIFY_MAX_AGE_MINUTES` old (default 30), it matches its sha256 sidecar, it passes `gzip -t`, and it ends with mysqldump's `-- Dump completed` trailer (a dump cut short has none; dumps taken before the trailer check could still carry a sidecar).
2. For each source bucket: the newest object manifest is at most `VERIFY_MAX_AGE_MINUTES` old and passes `gzip -t`, and `VERIFY_OBJECT_SAMPLE` random live objects (default 5) of it match their `sha256` and size in the backup. `VERIFY_OBJECTS=0` skips this in an environment without object backups.

It prints one `BACKUP_VERIFY_CHECK ok|FAIL …` line per check, then `BACKUP_VERIFY_PASS <n> checks`, or `BACKUP_VERIFY_FAIL <failed> of <n> checks failed` and exits 1, which marks the cron deployment failed. Run it by hand the same way (a one-off deployment with start command `verify.sh`) after any change to the backup service.

## Monitoring

- The `db-backup` run must print `DB_BACKUP_DONE` and one `OBJECT_BACKUP_PASS` per bucket within a few minutes of each quarter hour. A missing run, a `DB_BACKUP_FAIL` or `OBJECT_BACKUP_FAIL` line, or a cron job that exits non-zero is an incident: Railway marks the deployment failed and the project webhook (deploy-railway runbook, alerts) delivers it. `OBJECT_BACKUP_CARRYOVER` on more than a few consecutive runs means uploads outpace the bound.
- Daily: `db-backup-verify` must end in `BACKUP_VERIFY_PASS`; a failed run is an incident of the same rank (a missed backup, a stale manifest, a corrupt dump or object).
- Until an alert destination exists (owner checklist: Slack, Discord or email webhook), the failed-deployment notification of the two cron services is the alert; check both services' latest deployments daily.

## Restore: database

Never restore over production. Restore into a separate MySQL instance, verify, then import tenant rows (restore-single-tenant runbook) or switch the application to the restored instance.

1. Create or reuse a separate MySQL service in the environment (`mysql-restore` in staging) in the database's region. Note its private host and root password; do not paste either into a ticket.
2. Run `restore.sh` as a one-off deployment of the `db-backup` image with: `DST_HOST`, `DST_PW`, the `OBJECT_STORE_*` and `BACKUP_BUCKET`/`BACKUP_PREFIX` variables above, `RESTORE_NAME` (`oremedia` or `temporal`), `RESTORE_DB` (the database to create; default `oremedia`) and optionally `RESTORE_KEY` (a specific object; default the newest dump under the prefix). Keep `SRC_HOST`, `SRC2_HOST` and `SRC_PW` set: the guard below requires them. Start command: `restore.sh`.
   - **Guards, before anything is downloaded or dropped:** the script refuses (`RESTORE_FAIL`, exit 1):
     - when the environment name (`OREMEDIA_ENV`, else `RAILWAY_ENVIRONMENT_NAME`, compared in lower case) is empty or not one it knows: `staging` (or `staging-<suffix>`), `development`, `test`, `local`, or a production name. A laptop or one-off container without an environment name, or an environment named `live` or `main`, is refused, since nothing then says the target is not production. Set `OREMEDIA_ENV` to say which environment you are in;
     - when the environment name contains `prod`, unless `RESTORE_ALLOW_PRODUCTION` is set to the exact `DST_HOST` (a real production incident restores into a new, separate instance: type its host there, nothing else unlocks it);
     - when `DST_HOST` equals `SRC_HOST`, `SRC2_HOST` or a name in `PROTECTED_DB_HOSTS`;
     - when the target's server identity is not proven different from the source's: `SRC_HOST` and `SRC_PW` must be set, and `SELECT @@server_uuid` must answer on both `SRC_HOST` and `DST_HOST` with different values (the same value means another name or address of the source server and is always refused). An unset `SRC_HOST`, a source that cannot be reached or a target that does not answer yet is refused unless `RESTORE_ALLOW_UNVERIFIED_TARGET` is set to the exact `DST_HOST`: use it only when the source server is gone (an incident that lost it) or for a target you have checked by hand, and remove it afterwards. The log then says `RECOVERY_GUARD server identity not verified`. Start the target before the restore, so its identity can be read.
   - **Integrity:** the dump's sha256 must match its sidecar and the dump must pass `gzip -t` before the target database is touched; a mismatch fails with `RESTORE_FAIL checksum mismatch`. A dump without a sidecar (taken before sidecars existed, within the first 14 days after this change) is refused unless `RESTORE_ALLOW_UNVERIFIED=1`.
3. Read the log: `RESTORE_STEP <step> at +<s>s <UTC time>` lines give each step (`downloaded`, `checksum-verified`, `unpacked`, `loaded`, `verified`) and `RESTORE_PASS <name> from <key> in <N>s` is the evidence. The script fails if the table count in the restored instance differs from the dump's `CREATE TABLE` count.
4. Confirm the migration ledger: the last row of `__drizzle_migrations` in the restored instance must match the latest file in `packages/db/drizzle/`. A dump taken before the current release restores cleanly only when the migration set is roll-forward compatible (every migration is; `packages/db/src/migrations.integration.test.ts`).
5. Application steps after a full restore, before any worker reconnects: engage the `release_dispatch` and `agent_starts` kill switches (kill-switch runbook), point the api and workers at the restored instance (`DATABASE_URL`, `DATABASE_URL_RETENTION`), then run `publishing.publications.holdRestored` for every tenant until `hasMore` is false (restore-single-tenant runbook step 5) so nothing restored republishes, and re-apply deletion requests made after the restore point (step 6 there). Temporal: the `temporal` dump carries both databases with their CREATE DATABASE statements, so load it with `gunzip -c dump.sql.gz | mysql -h <host> -uroot` into the Temporal persistence instance before starting the Temporal server; in-flight workflows resume from their persisted history and re-read publication state, which the hold command has already changed.
6. Release the kill switches, run the smoke check against the environment (`SMOKE_BASE_URL=https://<web domain> pnpm smoke:prod`, deploy-railway runbook 3a), and record the drill or incident in the completion ledger with the `RESTORE_PASS` time.

## Restore: objects

Never restore into a live bucket. Restore into a new bucket (an incident: then point `OBJECT_STORE_BUCKET_ASSETS` or `OBJECT_STORE_BUCKET_RELEASES` of the api, worker-core and worker-render at it) or into a scratch prefix (a drill, or one tenant's objects to copy back by hand).

1. Run `restore-objects.sh` as a one-off deployment of the `db-backup` image with the `db-backup` variables plus: `RESTORE_BUCKET` (the bucket whose backup to restore, as named in the backup path), `DST_BUCKET` (the target), optionally `DST_PREFIX` (put before every key, ending in `/`), `RESTORE_KEY_PREFIX` (only keys starting with it, e.g. `assets/<tenant id>/` for one tenant), `RESTORE_MANIFEST` (a `manifest-<stamp>.tsv.gz` name for a point in time; default the newest), `RESTORE_INCLUDE_GONE=1` (also keys deleted from the source within the retention window, with their last content), `RESTORE_PARALLEL` (default 8) and `DST_OBJECT_STORE_ENDPOINT`/`_ACCESS_KEY_ID`/`_SECRET_ACCESS_KEY`/`_REGION` when the target is in another store (default the application store, `SRC_OBJECT_STORE_*`). Start command: `restore-objects.sh`.
   - **Guards:** the script refuses (`OBJECT_RESTORE_FAIL`) a `DST_BUCKET` equal (in any case) to `RESTORE_BUCKET`, `OBJECT_STORE_BUCKET_ASSETS`, `OBJECT_STORE_BUCKET_RELEASES` or a name in `PROTECTED_BUCKETS`; the backups bucket itself only under a `restore-scratch/` prefix; an empty or unrecognised environment name (as for the database restore: `staging`, `staging-<suffix>`, `development`, `test`, `local` or a production name); and a production environment unless `RESTORE_ALLOW_PRODUCTION` is the exact `DST_BUCKET`. An existing target key is never overwritten: it is verified like the others, and a different content fails the restore.
2. It copies each selected object from `objects/<sha256>` (checking the backup content against its `sha256` first, so a corrupt backup fails loudly), with its recorded content type, then reads every object back from the target and compares its `sha256` with the manifest. It prints `RESTORE_STEP objects-manifest|objects-copied|objects-verified at +<s>s <UTC time>` and `OBJECT_RESTORE_PASS <n> objects in <s>s`, or `OBJECT_RESTORE_FAIL …` with one `OBJECT_RESTORE_ERROR` or `OBJECT_RESTORE_MISMATCH <key> …` line per failed object and exits 1. A rerun after a partial restore verifies what is already there and copies the rest.
3. Release derivatives are rebuilt from assets when missing (recover-rendering runbook), so restore the assets bucket first when time is short.

## Recovery drill (staging, timed)

`drill.sh` runs the restores with timestamps for every step; the application steps are timed with `drill.sh mark`. It refuses to run without an environment name or with one it does not recognise, in production (unless `RESTORE_ALLOW_PRODUCTION` names the exact target, which a drill never sets), into a source database host or a server whose identity is not proven different from `SRC_HOST`'s (a drill never sets `RESTORE_ALLOW_UNVERIFIED_TARGET`), and into a live bucket; `restore.sh` and `restore-objects.sh` check the same again. Nothing in the drill writes to the staging MySQL or the staging media bucket.

Settings: the existing staging service `restore-rehearsal` (the `db-backup` image: Dockerfile path `infra/railway/db-backup/Dockerfile`, region us-west2, no cron, restart policy never) with the staging `db-backup` variables (references) plus `DST_HOST` = `${{mysql-restore.RAILWAY_PRIVATE_DOMAIN}}`, `DST_PW` = `${{mysql-restore.MYSQL_ROOT_PASSWORD}}`, `RESTORE_DB` = `oremedia`, `DST_BUCKET` = the `staging-backups` bucket name (the restore goes under `restore-scratch/drill-<stamp>/<bucket>/`; or a separate scratch bucket), and `DST_OBJECT_STORE_ENDPOINT`, `DST_OBJECT_STORE_ACCESS_KEY_ID`, `DST_OBJECT_STORE_SECRET_ACCESS_KEY`, `DST_OBJECT_STORE_REGION` = the backups bucket's (`OBJECT_STORE_*`) when the target is the backups bucket. Keep `SRC_HOST`, `SRC_PW` (the staging MySQL) set: the same-server guard requires them and refuses the drill without them. `RAILWAY_ENVIRONMENT_NAME` (`staging`) names the environment; set `OREMEDIA_ENV` only if the Railway environment has another name.

1. Detect and decide: `sh infra/railway/db-backup/drill.sh mark detect start` where you work (or note the time); the drill clock starts here. Then `… mark detect end`.
2. Start command `drill.sh all` on `restore-rehearsal`, deploy once. The log has `DRILL_STEP db-restore start|end <UTC time> elapsed=<s>s` with the `RESTORE_STEP` lines, then `DRILL_STEP objects-restore-<bucket> start|end …` with `OBJECT_RESTORE_PASS` per bucket, then `DRILL_PASS all in <s>s`. To run the halves as two parallel deployments (as in an incident), use `drill.sh db` and `drill.sh objects` instead.
3. Application steps, each between `drill.sh mark <step> start` and `drill.sh mark <step> end` (`DRILL_MARK <step> start|end <UTC time> <epoch>`): `kill-switches` (engage `release_dispatch` and `agent_starts`, kill-switch runbook), `repoint` (staging api, worker-core, worker-render, worker-ingest `DATABASE_URL` and `DATABASE_URL_RETENTION` to `mysql-restore`; buckets to the restored copy if it is a bucket), `hold-restored` (`publishing.publications.holdRestored` per tenant until `hasMore` is false), `smoke` (`SMOKE_BASE_URL=https://web-staging-6326.up.railway.app pnpm smoke:prod`, then release the kill switches), then point staging back at its own MySQL and buckets.
4. Clean up the scratch copy: `aws --endpoint-url "$OBJECT_STORE_ENDPOINT" s3 rm --recursive "s3://$BACKUP_BUCKET/restore-scratch/drill-<stamp>/"` (from a shell of `restore-rehearsal`), and set its start command back so a redeploy does not rerun the drill.
5. Fill the table below from the `DRILL_STEP` and `DRILL_MARK` times and record it in the completion ledger.

## Recovery time budget

| Step                                                                | Budget                                                           | Evidence                                                      |
| ------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------- |
| Detect and decide                                                   | 30 min                                                           | incident ticket; `DRILL_MARK detect`                          |
| Provision the restore instance and target bucket                    | 15 min                                                           | Railway service and bucket created                            |
| `restore.sh` (download, checksum, load, verify)                     | 60 min for a database up to about 5 GB                           | `RESTORE_PASS … in Ns`; `DRILL_STEP db-restore`               |
| `restore-objects.sh` (copy, read back, sha256), in parallel with it | 60 min for about 15,000 objects or 20 GB at `RESTORE_PARALLEL=8` | `OBJECT_RESTORE_PASS … in Ns`; `DRILL_STEP objects-restore`   |
| Re-point services, hold restored rows, re-apply deletions           | 45 min                                                           | holdRestored responses; `DRILL_MARK repoint`, `hold-restored` |
| Smoke and release                                                   | 30 min                                                           | smoke run; `DRILL_MARK smoke`                                 |

The databases and the objects restore in parallel (two one-off deployments), so the sum is three hours against the four-hour objective; run one after the other they take the whole four hours, which leaves no margin. The object row is an estimate (about three store requests per object at eight in parallel) until the staging drill measures it; the drill measures the restore rows and the application rows, and detection is an operator budget.
