# Runbook: reconnect a channel

**Symptom:** `channel_connections.status` is `refresh_needed` or `reconnect_needed`; metrics `oremedia.channels.token_refresh_failures` / `oremedia.channels.reconnect_needed` > 0; outbox event `channel.reconnect_needed` (the publisher notification hook); publications for the channel are `held` with reason `channel_active` after dispatch re-evaluation, or `held` with reason `channel_active` immediately after a disconnect.
**Owner:** publisher of the brand (customer) with platform support. **Exercised:** locally by `apps/worker-core/src/runbooks.integration.test.ts` ("reconnect a channel (7.4)"), which walks steps 1, 3, 5 and 6 through the composition root: a `reconnect_required` refresh flags the connection (`oremedia.channels.reconnect_needed` counted), `publishing.channels.list` shows `reconnect_needed` / `usable: false`, the due publication is held at dispatch with `channel_active` and never sent, reconnecting the same remote account keeps the connection id, rotates and shreds the credential, `publishing.publications.reschedule` re-releases the held row and it publishes; also `publishing.integration.test.ts` (refresh and disconnect details). **Needs a live environment for:** a real provider app's consent screen and revocation, the `tokenRefreshWorkflowV1` timer schedule on Temporal, and the provider-side suspension escalation.

1. Confirm the state: `publishing.channels.list { brandId }` shows the connection with `status`, `missingScopes`, `tokenExpiresAt`, `usable` and (RA-01) `health` with `healthCheckedAt`: `ok`, `token_expiring` (a refresh due before expiry failed transiently), `token_expired` (a read was refused for an expired token), `revoked` (the grant is gone: the refresh was refused for good, or a read was refused with a 401 the adapter classifies as `reconnect_required`), `unreachable` (the platform could not be reached at the last pull), `unknown` (nothing ran yet). The refresh workflow writes it with the status; the comment and metrics pulls (worker-ingest) write it through the adapter's own error classification (`channel.health` audit events, `fromState` → `toState`). Settings → Channels shows it as a chip beside the status with the reconnect action; the calendar's channel banner names a channel whose health needs a person. The audit trail carries `channel.token_refresh` events with `decision: denied` and the failure reason (`transient` / `reconnect_required`).
2. If `refresh_needed`: the connection's `tokenRefreshWorkflowV1` (workflow id `token-refresh:<channelConnectionId>`, task queue `core`) retried the refresh three times, spaced 2 / 10 / 30 min, under the per-connection lock; it has ended. Re-running the refresh means re-connecting (step 3) — there is no separate `channels.refresh` procedure (not in the router map; report if wanted). A successful refresh writes a **new** `credential_refs` row and crypto-shreds the old one (`rotated_at` + `destroyed_at`, key material overwritten).
3. If `reconnect_needed`: the publisher runs `publishing.channels.connect.start { brandId, providerKey, redirectUri }` and, after consent, `publishing.channels.connect.complete { state, code }` for the same provider and remote account. The connect flow finds the existing connection by `(providerKey, remoteAccountId)`, writes a new credential row, destroys the old one immediately (spec 17.5's 24 h bound), returns the status to `active` and emits `channel.connected`, which starts a fresh `tokenRefreshWorkflowV1` (USE_EXISTING joins one still running).
4. Missing scopes: `connect.complete` reports `missingScopes` against the capability's `requiredScopes`; `usable` stays false and the release check `channel_active` fails until they are granted.
5. Re-release each held publication: `publishing.publications.reschedule { publicationId, expectedVersion, scheduledFor }` (held → scheduled), which re-runs the release policy fail-fast and again at dispatch.
6. Verify: the next scheduled publication reaches `published` and `oremedia.publish.outcome_unknown` does not grow.

Disconnecting (RA-01): `publishing.channels.disconnect` disables the connection and holds its publications at once, and from that moment the stored token is unusable: the credential broker refuses to open a disconnected channel's credential for anything but the remote revoke (`credential_owner_disconnected`), and the metrics and comment pulls skip a disconnected channel. Where the provider's adapter can revoke the grant remotely (Meta, LinkedIn, X) the disconnect answers `remoteRevoke: 'requested'` and leaves the row to `channelRevokeWorkflowV1` (worker-core, a platform job started by the outbox from `channel.disconnected`, so a removed membership cannot hold it up), which asks the platform, records `channel.remote_revoke` in the audit trail (`revoked` / `failed` with `http_<status>` or the transport phase) and crypto-shreds the credential whatever the platform answered; an adapter without a remote revoke answers `not_supported` and the credential is shredded in the disconnect itself. The shred is bounded: `publicationSweeperWorkflowV1` shreds any credential still intact an hour after its disconnect (`channel.credential_shredded`, reason `disconnect_shred_floor`), whether the worker was down or the event dead-lettered. A failed remote revoke never blocks the local disconnect.

Escalate to platform if the provider app itself is suspended (all connections of that provider fail at once; the `publish-<providerKey>` queue can be paused by stopping that worker without touching the others).
