# Connection inventory: provider × capability certification

Finding PR-06 of the 4 October 2026 production-readiness audit: a provider marked certified said nothing about which
capabilities were exercised, so certification is now recorded per (provider, capability). This inventory lists
every registered provider with each certifiable capability, derived from the code at this commit and from recorded
evidence only:

- **Status** is what the registries report (`certifications(key)` on `providerRegistry`, `sourceRegistry` and
  `cmsRegistry`, the same states `operations.providers.list` returns to Settings → Channels and Settings →
  Destinations). `not supported` means the adapter or its capability register does not offer the capability;
  `certified` needs a record in the capability's `certifications` with its date, environment and evidence;
  anything else is `uncertified` (unknown means uncertified).
- **Evidence** is the recorded run behind a certification (the decision log entry and the harness recording), or
  why the capability is not supported. No run against designated test resources has been recorded for any
  provider, so nothing is certified.
- **Owner action** is what has to exist before the capability can be certified with
  `docs/runbooks/certify-a-provider.md`, followed by the harness command that records its evidence.

`tooling/scripts/certify/inventory.test.ts` fails when this table and the registries disagree, so a certification
recorded in code without updating this file (or the reverse) does not pass the unit suite.

## Summary

| Status        | Count |
| ------------- | ----- |
| certified     | 0     |
| uncertified   | 60    |
| not supported | 28    |
| total         | 88    |

Eight providers (four channels, three sources, one CMS) × eleven capabilities. What the product does with an
uncertified capability (server side):

| Capability                                       | Uncertified on a certified provider                                                                                                                                                             |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `connect`                                        | Blocked: connect start and completion refuse with `capability_not_certified:<key>:connect`; the provider reads `uncertified` in the providers listing                                           |
| `page_picker`                                    | Blocked: choosing among the accounts (channels) or targets (sources) of a grant is refused                                                                                                      |
| `publish_text`, `publish_image`, `publish_video` | Blocked: the variant fails validation with the capability issue, so `capability_valid` fails at release and nothing is scheduled to the platform                                                |
| `edit`, `delete`                                 | Blocked: `publication.edit_remote` / `delete_remote` refuse; the publication detail hides the action and says it is not certified (an article unpublish counts as `edit`)                       |
| `comment_reply`                                  | Blocked: the reply command refuses; the inbox says replies on the channel are not certified                                                                                                     |
| `analytics`, `token_refresh`, `reconnect`        | Labelled only: the settings screens show the state; metrics collection, report reads and token refresh keep running, since stopping them would break a live connection instead of protecting it |

Every provider is also uncertified at provider level (`certifiedAt: null`), so the registries refuse all of them for
tenants today whatever their capability records say.
