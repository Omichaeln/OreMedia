### D-03 consequence: second factor

Google does not reliably report second-factor use in ID token claims (`amr` is not part of Google's documented
claims), so Oremedia does not claim MFA for Google sign-ins: `users.mfa_enrolled` stays `false` for every user.
Consequence: a brand policy with `mfaRequired: true` (policy document v1) denies every Google-authenticated user
with `mfa_required` wherever that policy is consulted (review decisions today), so it must stay off. The
recommended control is outside Oremedia: enforce 2-Step Verification in the Google Workspace admin console for the
users of Oremedia, and set `AUTH_ALLOWED_DOMAINS` so only those Workspace accounts can sign in (runbook
deploy-railway.md section 1a). Revisit if Oremedia adds its own second factor or Google documents a reliable claim.

### D-03 follow-up: invitations are accepted on sign-in

**Decided (programme owner, 25 September 2026): keep the current behaviour.** Signing in with the invited, verified
Google account is the acceptance. The analysis that informed the decision follows. Behaviour: when a person signs in with Google, every pending invitation addressed to
their verified email is accepted automatically; there is no separate "accept" step. Consequence: an owner who knows
a user's email can add that user to their company, and the company then appears in that user's portfolio without
the user having agreed (the user gains access, never loses any; the inviting company learns nothing more than it
already knew, the email). Alternative: explicit accept — invitations show as pending in the portfolio and a
membership becomes active only when the person accepts (and can decline). Changing it touches the sign-in
resolution in `packages/modules/access/src/service.ts` and adds an accept/decline procedure and portfolio state.
